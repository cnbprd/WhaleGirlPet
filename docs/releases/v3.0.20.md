# v3.0.20 · 安全管家哈希查杀 + 引擎动作混合

本轮不是加功能条数，是给两个老模块各补一层「底层能力」。两边都先在 GitHub 上做了选型调研，只借机制、不引第三方运行时代码。

## 一、安全管家：从「规则匹配」补上「哈希查杀 + 自我证明」

| [Cisco-Talos/clamav](https://github.com/Cisco-Talos/clamav) | 7733 | 签名库与引擎分离、白名单先行；不搬 GPL 引擎 |
| [Neo23x0/Loki](https://github.com/Neo23x0/Loki) | 3809 | 判定链顺序：**hash → 文件名/路径 → 规则 → 行为**。hash 最便宜、零误判，应排第一 |

### 落地了什么

1. **SHA256 黑白名单**（`<数据目录>/hashes/black.txt`、`white.txt`，每行 `sha256  # 备注`）
   - 扫描每个文件先算哈希，命中黑名单直接判 **高危 45 分**，命中白名单**直接放过**；
   - **白名单优先**：同一哈希两边都有时按信任处理——误报修正就该这么来；
   - 名单按目录 mtime 缓存，改文件不必重启；名单为空时零开销（不算哈希）。
2. **EICAR 两层自证**（面板「安全体检 → 自测扫描能力」）
   - 规则层：内置 `AV-EICAR` 规则对标准串做纯内存匹配；
   - 端到端：真写一个 EICAR 文件再扫；若被系统实时防护锁住读不了，记为 `blocked=system`——**那同样算检出，只是动手的是 Defender**；
   - 对照组：同时写一个无害脚本，必须零命中。
3. **READ-BLOCK 识别**：文件存在但读不开（Errno 13/22）不再静默跳过，报告里标一条 info「内容读取被安全软件拦截」。
4. 面板新增「哈希名单」按钮，一键打开目录并按说明头建好两个名单文件。

### 实测（`tools/test_guard_hash.py`，18/18）

| 项 | 结果 |
| :-- | :-- |
| 规则层认出 EICAR | ✅ |
| 端到端 EICAR 检出 | ✅ 命中 `AV-EICAR`，40 分 |
| 无害对照误报 | 0 条 |
| 自测耗时 | 47.8 ms（16 条规则） |
| 黑名单命中 | ✅ 45 分，备注带出 |
| 白名单优先 | ✅ 零命中 |
| 名单清空后恢复判定 | ✅ |
| 8MB 文件流式 SHA256 | 33.6 ms |
| 名单启用后 20 次扫描 | 567 ms（≈28 ms/次，主要是 8MB 哈希） |

**本项目实测到的一件事**：Windows Defender 会对含 EICAR 串的文件直接拒绝内容读取（文件还在、`getsize` 正常，`open` 报 `Errno 22`，持续 2 秒以上）。所以自测不能假定「写下去就一定能读回来」，必须把 `blocked=system` 当作有效结果——这也解释了老版为什么某些文件「扫了但没结论」。

### 学了什么

| 项目 | star | 用到的那一条 |
| :-- | --: | :-- |
| [EsotericSoftware/spine-runtimes](https://github.com/EsotericSoftware/spine-runtimes) | 5381 | `mix duration` 交叉淡入、track 排队、`timeScale`。**只借鉴机制**：Spine Runtime 是商业授权，代码未采用（`docs/THIRD_PARTY.md` 口径不变） |
| [Inochi2D/inochi2d](https://github.com/Inochi2D/inochi2d) | 1887 | 参数驱动的实时 puppet，验证「时间轴 + 参数混合」适合桌宠这种低帧率场景 |
| [Inochi2D/inochi-creator](https://github.com/Inochi2D/inochi-creator) | 1269 | 分层与参数命名规范 |

### 落地了什么（`app/anim_engine.py`）

1. **交叉淡入**：`Timeline.play(clip, mix=0.15)`——切动作时旧 clip 继续推进，与新 clip 按权重混合；
   权重用 `smoothstep`（3w²−2w³）而不是线性，两端加速度为 0。
2. **排队**：`queue(clip)`，单次动作放完自动接下一个；接缝给 0.12s 短淡入。
   顺带修掉一个真 bug：收尾那一帧的事件（例如 hop 的最后一次 `land`）会被切换重置吞掉，现在显式保留。
3. **变速**：`time_scale`（夹在 0.05×~8×），事件点按实际推进时间触发。
4. `pose_now()` 改为返回本帧**已混合**的姿态（原来只返回当前 clip 的姿态，等于混合白做）。
5. `pet_window.do_action(key, duration_ms, then="", mix=0.15)`：默认 0.15s 淡入，`then` 可串下一个动作。

### 实测（`tools/test_anim_mix.py`，12/12，crab → hop，30fps 采样 bob）

| 指标 | 硬切 | 0.15s 混合 | 变化 |
| :-- | --: | --: | :-- |
| 切换帧位移 | 16.46 px | 2.94 px | **−82%** |
| 切换处速度突变 | 15.20 px/帧 | 11.15 px/帧 | −27% |
| 混合窗口帧数 | — | 5 帧（0.15s） | 符合预期 |
| hop 排队 tumble | — | 3 次 `land` 全保留 + 自动接 tumble | ✅ |
| 0.5× 变速 2 秒 | — | 只推进 1.00s | ✅ |
| 混态每帧开销 | — | 10 µs | 可忽略（16ms 帧预算的 0.06%） |

**一条要记下的局限**：0.15s 只能压住「位置」不跳，压不住「速度」——hop 这种起始 30px/帧 的爆发动作，速度突变只降了 27%。要速度也连续，得让每个动作自带「进入速度匹配」，那是更大的一步，本轮没做。

## 四、怎么用

1. 面板「安全体检」→「自测扫描能力」：一行字告诉你规则层、端到端、误报、耗时、名单规模。
2. 「哈希名单」：打开目录，往 `black.txt` 里贴已知恶意样本的 SHA256（可带备注），下次扫描直接命中。
3. 动作切换现在默认 0.15s 淡入；帧率不足或想「硬一点」，把 `do_action` 的 `mix` 传 0。

## 五、没做的（诚实清单）

- 没接 YARA C 库：Windows 上要编 `yara-python`，体积与兼容成本不划算；现有 JSON 规则已覆盖同类判定形状。
- 没做隔离区（quarantine）：仍坚持「只报不杀」，处置交给 Defender。
- 没做实时文件监控（filesystem watcher）：桌宠常驻监听全盘 IO 代价高，收益不匹配。
- 没做速度匹配式过渡：见上面那条局限。
