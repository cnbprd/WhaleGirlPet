# 鲸鱼娘桌宠 v3.0.19：三个未完项的实测结论（首帧 / 音频 / 图片上限）

上一版留的三个扣分点，这版全部做完，结论有能用的也有做不通的。

## 一、真实首帧：不是内存近似了，是抓像素验的

新工具 `tools/first_frame.py`：Win32 `EnumWindows` 找该 exe 的可见窗口（onefile 要连父/子两个进程一起查），拿到矩形后用 `ImageGrab` 抓图算灰度标准差，`std > 8` 才算"画面真的出来了"。

| 版本 | 进程出现 | 窗口可见 | 首帧有内容（std 峰值） | 三次实测 |
| :-- | --: | --: | --: | :-- |
| onefile（v3.0.16，69.4MB） | 0.05 s | 4.28 s | **4.28 s**（std 57.2） | 3.82 / 3.72 / 3.72（中位 **3.72 s**） |
| onedir（v3.0.19，4.4MB exe） | 0.01 s | **0.65 s** | **0.65 s**（std 57.5） | 0.64 / 0.59 / 0.78（中位 **0.64 s**） |

结论：真实首帧 **3.72 s → 0.64 s，省约 3.1 s（约 5.8 倍）**，和上一版内存近似（0.76 s / 0.61 s）对得上。单次数字有抖动（构建后第一次跑到过 2.85 s），所以给的是三次中的中位数。

## 二、音频：接口收，模型不吃 —— 本地听语音这条路目前做不通

`input_modalities` 里报着 `audio`，但那是模型元数据，不等于能用。三种写法实测（2.5s / 16kHz / 单声道 wav，base64 104KB）：

| 写法 | 结果 |
| :-- | :-- |
| `{"type":"input_audio","input_audio":{"data":..,"format":"wav"}}` | **200 通过**，回答「抱歉，我无法处理音频内容。请提供文本」 |
| `{"type":"audio_url","audio_url":{"url":"data:audio/wav;base64,..."}}` | 400 `unsupported content[].type` |
| `{"type":"input_audio","input_audio":"<b64>"}` | 500 `Invalid base64 value` |

引擎日志同时有两条关键行：

```
W init_audio: audio input is in experimental stage and may have reduced quality:
I srv load_model: loaded multimodal model, '...mmproj-gemma4-e2b-f16.gguf'
```

即：引擎的路由收 `input_audio`（实验性），这份 mmproj 也被加载了，但**音频没有被真正编码进 token**，模型只能回"不能处理音频"。

所以"听语音"保持现有链路：`app/voice_cmd.py` 用 Windows `System.Speech.Recognition` 本地转文字 → 文本进 LLM。不要再往本地音频模型上砸时间，除非换到带 audio 编码器的 mmproj 并确认 llama.cpp 侧支持（目前没有可用文件）。

## 三、图片上限：不是分辨率，是 base64 请求体长度

上一版我用 960px 撞了 400，误判成"分辨率上限"。这版做了对照实验（`tools/probe_image_limit.py`，同一张 `docs/api_card_v315_on.png`，分别以默认参数、`--image-max-tokens 8192`、`--image-max-tokens 16384 --image-min-tokens 256` 起引擎）：

| 尺寸 | jpg 原始 | data url | 默认参数 | +image-max-tokens 8192 |
| :-- | --: | --: | :-- | :-- |
| 512px（453×512） | 21 KB | 28 KB | ✅ 17.2 s | — |
| 640px（566×640） | 30 KB | 40 KB | ✅ 19.1 s | — |
| 768px（680×768） | 39 KB | 52 KB | ✅ 21.8 s | ✅ 22.3 s |
| 960px（850×960） | 53 KB | 71 KB | ✅ 29.1 s | ✅ 28.9 s |
| 1280px（1133×1280） | 74 KB | 99 KB | — | ✅ 50.9 s |

三条结论：

1. **`--image-max-tokens` 不改变成功/失败**，768/960 在两个参数下都过。它是 token 预算，不是门槛。
2. 真正卡住的是 **data url 长度**：上一版失败那次是 156 KB（真实屏幕截图内容更杂，JPEG 更大），这次 99 KB 顺利通过；104 KB 的音频也能进。安全线按 **≈100 KB** 算。
3. 耗时几乎全花在**生成**上（提示词要求"逐字写出标题"，`max_tokens` 120 被用满）：512px 都要 17s。短问短答时 512px 只有 4~5s（`tools/live_vision.py` 实测 4.4s）。

### 读字这件事，抬分辨率救不了

同一张深色 API 卡片图，模型在 512/640/768/960/1280px 的回答分别是：

- 「0 0 0 0 …」（512、640）
- 「大量的空格和乱码/方块符号」（768、960、1280）
- 「没有明显可识别的完整标题」

图里的 `EdgeOne Makers` 一个字都没读出来。**Gemma 4 E2B 不是 OCR 模型**，它做的是场景级理解（"这是网页/文档/界面/一堆按钮"）。要精确读字，应该走专门的 OCR（例如 `byted-mediakit-image` 的「读取图片文字」能力），不要再给视觉模型加分辨率——那只会更慢。

## 四、这版顺手加的唯一功能：清晰度可调

`config.json` 新增：

```json
"vision_max_side": 512
```

- 512：实测最快（看图 4~5s），够判断场景 —— **默认**。
- 768：细节更多但仍受阻于模型本身读字能力，耗时随生成长度上升（本次实验 21.8s 是在长输出条件下）。
- 别超过约 100 KB 的 data url（大致对应 1280px 以上），会直接 400。

`app\vision.py` 的 `capture_screen / to_data_url / vision_message` 全部接受 `max_side` 参数；`act_look_screen` 从配置读取。
