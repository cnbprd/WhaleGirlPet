## v3.0.5

这一版**没有功能改动**，只是把 v3.0.4 的说明补成实测结论（v3.0.4 页面发布时正文还没核实完，这里一次性写清）。功能与 3.0.4 完全一致，装哪个都一样。

### 3.0.4 带来的记忆修复（本页为准）

之前桌宠被任务管理器强杀或崩溃时，本地推理子进程没人回收，实测一个 `dafeiyu-server` 从 02:47 活到 17:15，独占 **2388.6MB** 内存，直到重启电脑。

| 改动 | 实测 |
|---|---|
| Job Object（`KILL_ON_JOB_CLOSE`）绑定子进程，父进程一死系统连子进程一起杀 | 父进程 `os._exit(1)` 硬退后 2 秒，子进程消失，零残留 |
| 启动时清理上次残留的推理进程 | 实测杀掉 1 个残留 |
| 引擎闲置 20 分钟自动卸载（可在「设置→自定义模型」改为 0 = 从不卸载） | `stop()` 后引擎内存 **0MB**；下次聊天自动重载，5.7–8.1 秒 |
| 引擎加 `-np 1`（单人对话，4 个 slot 白占 KV） | 工作集 4647.6 → 4492.4MB |
| 聊天历史改流式读取，内存里只留最近 240 条 | — |

### 引擎那 4.5GB 到底是什么（逐段核实，不是估算）

用 `VirtualQueryEx` + `GetMappedFileNameW` 遍历引擎进程地址空间，系统直接返回了文件名：

```
2525.9MB  MEM_MAPPED  COMMIT  qwen35-4b-Q4_K_M.gguf
```

| 构成 | 体积 | 性质 |
|---|---|---|
| gguf 文件映射段 | 2526MB（当前驻留约 2144MB） | 系统可丢弃，不占提交额度 |
| 私有提交（KV cache、计算缓冲、堆） | 2348MB | 真实占用，只能停进程才放 |

反向验证：`EmptyWorkingSet` 后工作集从 4493MB 掉到 3MB，但**私有提交仍是 2348MB 没变**——如果权重是 `read()` 读进堆的，提交至少 2526MB，与 2348MB 矛盾，所以权重确实走文件映射。

结论：空闲卸载一次能还回全部约 4.5GB；只想让任务管理器数字好看的话，映射那 2.1GB 在系统内存吃紧时会自己掉。

### 实测数据（本机 GTX 1060 6GB / 31.9GB 内存）
| 场景 | 内存 |
|---|---|
| 桌宠冷启、未用本地模型 | 95MB |
| 引擎加载完成（-np 1） | 4492MB（私有提交 2348MB） |
| 引擎 stop 后 | 0MB |
| 修复前的孤儿进程 | 2388MB，持续 14.5 小时 |
